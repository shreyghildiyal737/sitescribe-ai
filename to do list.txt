MUST FIX BEFORE GOING PUBLIC / DEPLOYING (security)
====================================================================

[ ] 1. JWT SECRET  (CRITICAL)
    Problem: application.yml ships a hardcoded, PUBLIC default JWT secret,
    and backend/.env has JWT_SECRET= (empty). In production the app would
    fall back to the known default — anyone could forge a valid token for
    ANY company = full account takeover.
    Fix: set a strong JWT_SECRET env var in production (Railway/host).
    Generate one with:
      node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"

[ ] 2. ROTATE API KEYS  (HIGH)
    Problem: Groq + Gemini keys are stored in plaintext in
    construc-torr/*.txt and were shared in chat.
    Fix: regenerate (rotate) both keys before public launch; never commit
    keys; keep them only in env vars / a secrets manager.
      - Groq:   https://console.groq.com/keys
      - Gemini: https://aistudio.google.com/apikey

[ ] 3. LOGIN USER-ENUMERATION  (MEDIUM)
    Problem: AuthService.login returns different messages for
    "No account found" vs "Incorrect password" — lets attackers discover
    which emails are registered.
    Fix: return one generic message, e.g. "Invalid email or password."
    File: backend/src/main/java/com/sitescribe/auth/AuthService.java

[ ] 4. SWAGGER / API DOCS ARE PUBLIC  (MEDIUM)
    Problem: /swagger-ui/** and /v3/api-docs/** are open to everyone —
    exposes the full API schema.
    Fix: in production, disable or require auth:
      springdoc.api-docs.enabled=false
      springdoc.swagger-ui.enabled=false
    (or protect behind authentication)

[ ] 5. NO RATE LIMITING ON AUTH  (MEDIUM)
    Problem: public /api/auth/** (bootstrap + login) has no rate limiting —
    allows brute-force and signup spam.
    Fix: add rate limiting (e.g. bucket4j / a gateway / Cloudflare) and/or
    a captcha on register.
